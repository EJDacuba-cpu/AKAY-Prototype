## Scope and completion status

This is the coverage inventory and interface contract, not a claim that every adapter is complete. **Shared infrastructure and the Facilities reference adapter are implemented in source. Clinical recovery and its backend lifecycle guards are wired in source and undergoing union verification. Other business-form adapters remain Task 4 work.** `FORM_DRAFTS_ENABLED` remains false; BHC drafts remain disabled and the existing RHU draft flag remains true. ## Identity, schema and authorization

Schema version is `1`. Context syntax is exactly `new` or `<registered-subject>:<positive-integer-id>`; every allowed mode/subject pair is listed below. No account/facility identity is trusted from the request. Server scope is `<home-role>:admin` for Admin, otherwise `<home-role>:<working-role>:<current-facility-id>`. Clinical device scopes append a permissions fingerprint, preventing re-use of a full old clinical snapshot after duty changes. `scope` should be treated as an opaque server value by clients.

One active slot is SHA-256(owner + scope + form_type + mode + context_key). PostgreSQL/SQLite enforce a nullable unique `active_slot`; terminal rows release the active slot but retain an owner+transaction UUID unique tombstone. Writes serialize on the user row and then the draft. A new UUID starts only a new transaction after lookup/terminal checks. Different form actions (e.g. mother/father link, account profile/access, stock release/disposal) have separate types.

All endpoints require existing authenticated, active, activated/password-current and working-facility middleware. Registry checks required role, action permission and dependent read permissions; target lookup uses existing FacilityAccessService, provider management, household facility ownership or MonitoringHandoffService rules. Admin does not gain clinical write access from this API. Ordinary details/status/keys are private to the current owner and context. Consultation device keys are also private; existing server consultation drafts remain shared according to clinical review policy.

Payloads contain only explicit schema fields. A `true` leaf accepts bounded scalar/null input, including temporarily incomplete dates/numbers. Object/list nodes reject unregistered fields recursively; `*` permits numeric list/map keys only. No complete domain validation occurs on a checkpoint. Final validation is unchanged. Maximum JSON payload is 131072 bytes, scalar string 20000 characters, each object/list 100 entries. Base revision is null, integer, bounded string, or up to 20 named integer section revisions. Store only selected target IDs and entered fields; refresh all fetched metadata after Resume. Use explicit mapping before normalization, because final serializers may trim, drop unchecked rows, coerce invalid numbers or fill defaults.

## Personal API

All paths are under `/api`, and responses use `Cache-Control: no-store, private`. Successful JSON is under `data`. Writes/key operations share a configured per-owner 30/minute limit; ordinary API throttling also applies.

- `GET /form-drafts/lookup?form_type&mode&context_key`: exact authorized active-slot metadata or null. No payload.
- `GET /form-drafts/status?form_type&mode&context_key&transaction_uuid`: exact owner/context transaction status metadata or null, including terminal `consumed`, `discarded`, `expired`. No result or payload. Query this before unlocking/recreating device input after reload. `consumed` means stop retrying and refresh official domain state; do not reconstruct secrets/consent just to replay.
- `POST /form-drafts`: `{form_type,mode,context_key,transaction_uuid,schema_version:1,payload,base_revision}`. Returns 201 metadata, version 1. Any active-slot or previously used transaction conflict returns 409 safe metadata; it never overwrites another draft.
- `GET /form-drafts/{opaque-id}`: current authorized active metadata plus payload; terminal/expired detail is 404. Metadata contains `id,form_type,mode,context_key,scope,transaction_uuid,schema_version,version,status,base_revision,last_saved_at,expires_at`.
- `PUT /form-drafts/{id}`: same identity/body as create plus expected `version`. Identity/revision/terminal mismatch returns `409 FORM_DRAFT_CONFLICT`. Changed payload/base revision increments version and refreshes seven-day expiry. Identical writes preserve version/save/expiry timestamps.
- `DELETE /form-drafts/{id}` body `{version}`: 204; matching active revision becomes discarded and payload/base revision/key material is removed. Stale/terminal writes cannot resurrect it.

`GET status` can return a device-only key transaction with `id:null,version:null` and status active/discarded/expired. Do not mistake this for a server-saved draft.

## Authenticated device-key protocol

`POST /form-drafts/device-key` receives `{form_type,mode,context_key,transaction_uuid,key_id?,key_version?}`. `key_version`, when supplied, must be 1. The response `data` contains `{key_id,key_version:1,key_material,expires_at,form_type,mode,context_key,scope,slot_hash,transaction_uuid}`. `key_material` is base64 encoding of 32 random bytes. Import it as a non-extractable AES-GCM Web Crypto key and retain it **only in live memory**. Persist the opaque key ID/version/identity and ciphertext envelope, never key material/CryptoKey/password/token. Every reacquisition reauthorizes owner, active assignment, action and subject.

A key is scoped to owner + current form/subject slot + transaction UUID, encrypted at rest with Laravel Crypt. It has a fixed seven-day lifetime from issuance; device envelope expiry must not exceed `expires_at`. Reads do not extend that lifetime. Inaccessible or expired keys are errors, not empty recovery. Preserve protected ciphertext on logout/session expiry while clearing plaintext/live keys before another account initializes. Legacy persisted keys may be used only during authenticated owner/context migration, then removed.

Device-only personal Discard uses `POST /form-drafts/device-key/retire` with identity + transaction UUID + key ID. It returns 204 and retains a terminal key tombstone. An active server draft must first be discarded by its expected version, otherwise retirement returns 409. A stale device transaction cannot later create a fresh server draft. Do not use this endpoint to discard consultation workflow records.

Clinical key-only registration: `form_type:'consultation'`, stable `mode:'edit'`, BHC `context_key:'patient:<id>'`, RHU `context_key:'visit:<actual-started-id>'`, transaction UUID is the existing consultation UUID. The key API also accepts create mode, but clients must keep one stable mode for the whole transaction; do not switch when a server draft ID appears. RHU checks encode/finalize authority and actual in-consultation visit UUID/state. Existing clinical draft status/facility/target is checked if present; consumed/discarded/expired consultations cannot reacquire keys. Generic CRUD/status/commit rejects this key-only type. Task 3 integrates clinical terminal/status lookup through existing clinical APIs.

Task 3 terminal hook: call `app(FormDraftRecoveryKeyService::class)->retireClinical($healthRecordDraft)` **inside** its existing successful consume/discard transaction, after setting its terminal status. This scrubs matching consultation UUID+subject keys across checkpointing owners; it never changes clinical workflow state itself.

## Explicit final commit contract

Frontend service methods accept an explicit options object `{draftCommit:{id,version,transaction_uuid}, ...existingOptions}`. Forward it as `X-Form-Draft-Id`, `X-Form-Draft-Version`, `X-Form-Draft-Transaction`. No ambient global mutation context and no draft inference by scraping request bodies.

Controller integration signature:

```php
FormDraftCommit::run(
    Request $request,
    string $formType,
    string $mode,
    string $contextKey,
    array $mutationPayload,
    Closure $mutation,
    Closure $authorize,
): Symfony\Component\HttpFoundation\Response
```

The endpoint supplies its own known form/action/target and normalized final mutation payload. `$authorize` checks current domain access before both first execution and replay. `$mutation` keeps existing domain validation/confirmation/permission and save logic. It must return a successful HTTP response; failures/exceptions roll back both domain writes and draft consumption. Without any commit headers, legacy endpoint behavior is preserved; partial headers fail validation. `metadata(Request): ?array` is available separately.

The helper locks owner/draft, verifies exact expected revision/slot/UUID, HMAC-fingerprints the endpoint-supplied payload, executes mutation and consumes matching draft in one database transaction. Same identity/version/payload retry returns the encrypted stored response once; changed payload or wrong target/action conflicts. Stored response is encrypted, retained seven days after success, then scrubbed; the terminal identity survives and cannot cause a second official save. `status` remains usable without replaying original secrets/consent. Final domain saves needing more than one endpoint must have a genuine shared final boundary. External mail/notifications must be scheduled after commit or through an existing durable outbox; a database rollback cannot undo an already sent email.

After authoritative success, frontend `complete()` stops queued checkpoints and deletes only that local identity. After a lost response/reload, query exact transaction status first. Never start a fresh UUID for a consumed transaction, and never report a version conflict as successful save.

## Retention and database verification

`form-drafts:prune` is registered on existing Laravel scheduling infrastructure, daily without overlap. It scrubs expired personal payloads/base revisions, committed response contents and key ciphertext, preserving non-payload tombstones. Reads enforce timestamps immediately; no scheduler timing is used to authorize stale content.

Feature tests use the configured SQLite `:memory:` database via `RefreshDatabase`; no non-test migration was run. Database unique-index behavior is tested directly and the implementation uses row locks for PostgreSQL. **Actual concurrent PostgreSQL contention has not been verified**; no safe isolated PostgreSQL test database was supplied. No offline official mutation queue is introduced.
